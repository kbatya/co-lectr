### 2. README, architecture diagram, spin-up

The friction, the two-layer rationale, a Mermaid architecture diagram, config and CLI tables, what
Firestore stores and what it deliberately does not, the security posture, a status table, and the
hackathon stack mapping. Also `.env.example`, since `.env` is git-ignored and the variable names
were written down nowhere.

Two deliberate choices in it:

- **The Cloud Run and PR-comment nodes are drawn dashed and labelled *planned*.** Solid edges are
  only what is implemented and tested. Nothing is claimed that does not run.
- **Layer 1 is documented as needing no credentials at all.** A judge can clone, `pip install`, and
  see the real per-class digest without a Gemini key or a GCP project — the cheapest possible path
  to "reasonably applies the requirements" in Stage One.

The diagram was verified by rendering: Mermaid 11, `RENDER OK`, 13 nodes, 17 edges, ratio 1.25, so
it scales to GitHub's column width without becoming an unreadable strip.

The clone line names the directory `co_lectr`. The repository *is* the package and every import is
`co_lectr.*`, so a judge cloning to the default `co-lectr` gets a directory Python cannot import.

## Decisions taken

| # | Decision | Rationale |
|---|---|---|
| 1 | Only rules the current submission hits **again** are passed to the model | A rule the student has since fixed invites a question about code that is no longer there |
| 2 | The history instruction lives in `reviewer.INSTRUCTION`, not the shared `REVIEW_POLICY` | `agent.py` shares the policy but has no Firestore wiring; telling a model about a history it cannot see is an invitation to invent one. A test pins the separation |
| 3 | The profile is read only on the branch that actually reviews | A cached review costs no Firestore read. A test fails if that changes |
| 4 | The prompt states counts, and the model is told never to guess which submission | `recurring` holds occurrences per rule, not dates — see the limitation below |
| 5 | Provisioning and Classroom (build-order steps 6–7) are cut from hackathon scope | Pilot-readiness, not judged. They stay on the pilot path |

## Known limitation

`recurring` counts **occurrences per rule**, with no record of which milestone they came from. The
reviewer can therefore say *"three times in your previous submissions"* but not *"you hit this in
PR #2"*. Making the PR-specific version work is roughly five lines in `store.record` — an
`ArrayUnion` of the milestone per rule — and was left out as beyond the scope of this session.
